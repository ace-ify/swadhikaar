# Superseded migrations — history only, DO NOT RUN

These five files built the database incrementally between 2026-07-30 and 2026-08-23.
They have been replaced by a single squashed baseline:

    supabase/migrations/000_baseline.sql

They are kept here for archaeology — to answer "why is this column shaped like
this?" — and moved **out of `supabase/migrations/`** so no tool picks them up.

## Why they were retired

The live database had **21 applied migrations while only 5 files existed on disk**.
The schema that built production was largely not in version control, and the files
that *were* present had drifted into being actively dangerous:

1. **`user_roles` was created by no file.** Every authorisation path reads it —
   `is_admin()`, `current_app_role()`, the Next.js proxy, `auth-context.tsx`. A
   database rebuilt from these files had no roles table, so all authorisation broke.

2. **`001_initial_schema.sql` lines 349–378 contain eight `admins_full_access`
   policies** that read `auth.users.raw_user_meta_data->>'role'`. A user can write
   their own `user_metadata`, so those policies let any account make itself admin.
   They were removed from the live database long ago (verified: 0 matching policies
   in `pg_policies`), but running this file would recreate them.

Together those meant `supabase db reset` produced a database with **no roles table
and user-writable admin access** — while looking like it had worked.

## What the baseline contains instead

Generated by reading `pg_catalog` on the live database, and verified against it:

| | |
|---|---|
| Tables | 17 (incl. `user_roles`) |
| Policies | 48 |
| Functions | 11 |
| Views | 1 (`security_invoker`) |
| Triggers | 1 |
| Cron jobs | 2 |
| Workflow rows | 8 (configuration the seam depends on) |
| `raw_user_meta_data` policies | 0 |

`supabase db dump` was unavailable on this project (the CLI cannot create its login
role: `permission denied to alter role`), which is why the baseline was assembled
from catalog queries rather than the standard dump.

## Applying the baseline to a fresh database

    psql "$DATABASE_URL" -f supabase/migrations/000_baseline.sql

Then three things the migration deliberately does not do:

1. **Vault secrets** — the recovery-call cron job reads `project_url` and
   `edge_function_key` from `vault.decrypted_secrets` by name. Secret *values* are
   never committed. Create them with `select vault.create_secret('<value>', '<name>')`.
   Without them the job logs a NOTICE and returns 0 rather than failing.
2. **Roles** — insert your own `user_roles` rows. Nothing can self-assign a role
   through the API; that is the point of the table.
3. **Patient data** — `python backend/seed_data.py` if you want sample records.
